# PPPoE Load Balancer — Agent Workflow Instructions

> **Purpose:** This document defines the workflow for agents working on the multithreaded PPPoE implementation. Follow these instructions when claiming tasks, updating status, or submitting changes.

---

## 1. Before Starting Work

### 1.1 Read the Master TOC

Before starting any work, read [`0.0-PPPoE-TOC.md`](./0.0-PPPoE-TOC.md) to understand:
- The overall project structure
- Document dependencies
- Task dependencies in the implementation

### 1.2 Identify Your Task

1. Open [`3.0-PPPoE-Implementation-Tasks.md`](./3.0-PPPoE-Implementation-Tasks.md)
2. Find the task you want to work on
3. Verify its status is `NOT STARTED`
4. Check dependencies are met (all prerequisite tasks are `COMPLETED`)

### 1.3 Check Current Implementation State

Review existing code before starting:
- `sys/netgraph/ng_pppoe_lb.c` — Kernel module
- `sys/netgraph/ng_pppoe_lb.h` — Kernel header
- `usr.sbin/ngctl/pppoe_lb.c` — ngctl commands
- `libexec/pppoed/pppoed.c` — pppoed daemon

## 2. Task Claiming Protocol

### 2.1 Claiming a Task

When you start working on a task:
1. Update the task status in `3.0-PPPoE-Implementation-Tasks.md` from `NOT STARTED` to `IN PROGRESS`
2. Add your agent identifier and timestamp
3. Document any assumptions or decisions made during analysis

### 2.2 Task Status Definitions

| Status | Meaning | When to Use |
|--------|---------|-------------|
| `NOT STARTED` | Task has not been touched | Initial state |
| `IN PROGRESS` | Actively working on task | During implementation |
| `COMPLETED` | Task done, verified, tested | Final state |
| `BLOCKED` | Waiting on another task | When blocked by dependency |
| `DEFERRED` | Postponed for later | When skipping for now |

### 2.3 Task Format in Document

```markdown
| # | Task | Description | Status | Owner | Dependencies | Files | Notes |
|---|------|------------|--------|-------|--------------|-------|-------|
| 1.1 | Task Name | What it does | NOT STARTED | | 1.0 | `file.c` | |
```

When working on a task:
```markdown
| 1.1 | Task Name | What it does | IN PROGRESS @agent_name | agent_name | 1.0 | `file.c` | Analysis complete |
```

## 3. Implementation Guidelines

### 3.1 Code Style

Follow FreeBSD kernel coding standards:
- Indent with tabs (not spaces)
- Maximum line width: 80 characters
- Use `KASSERT()` for invariant checks
- Use `mtx_lock()`/`mtx_unlock()` for mutex protection
- Follow existing patterns in `sys/netgraph/*.c`

### 3.2 Kernel Module Requirements

For `ng_pppoe_lb.c`:
- Include `ng_pppoe_lb.h` header
- Implement all required `ng_*` hooks
- Register node type with `ng_newtype()`
- Use `M_NETGRAPH_PPPOE_LB` malloc type
- Implement proper shutdown sequence

### 3.3 Userland Requirements

For `pppoed.c`:
- Follow existing pppoed code patterns
- Use `daemon(3)` for backgrounding
- Parse `/etc/ppp/pppoe.conf` for configuration
- Support `-L` flag for multi-worker mode
- Write PID file for `rc.d` integration

### 3.4 Build Requirements

All components must compile without errors:
- Kernel module: `sys/modules/netgraph/pppoe_lb/`
- ngctl: `usr.sbin/ngctl/`
- pppoed: `libexec/pppoed/`

Verify build with:
```bash
cd sys/modules/netgraph/pppoe_lb && make
```

## 4. Testing Requirements

### 4.1 Before Claiming "Completed"

All tasks must pass:
1. **Compilation**: Code compiles without errors
2. **Unit Tests**: Any relevant tests pass
3. **Documentation**: Relevant docs updated

### 4.2 Testing Order

1. **Build verification** (compile first)
2. **Static analysis** (manually review code)
3. **Unit tests** (run existing tests)
4. **VM tests** (if applicable, run in VM)

### 4.3 What NOT to Do

- ❌ Do NOT load kernel module in non-VM environment
- ❌ Do NOT commit untested changes to production
- ❌ Do NOT skip compilation verification
- ❌ Do NOT modify other unrelated tasks

## 6. Completion Protocol

### 6.1 Pre-Submission Checklist

- [ ] Code compiles without errors
- [ ] All tests pass (if applicable)
- [ ] Documentation updated
- [ ] Task status marked `COMPLETED`
- [ ] No merge conflicts with other tasks

### 6.2 Submission Summary

When submitting, provide:
1. **Summary**: What was implemented
2. **Changes**: Files modified (with line numbers if significant)
3. **Verification**: How it was tested
4. **Notes**: Any limitations or follow-up items

### 6.3 Example Submission

```
## Summary
Implemented Phase 1.5 task 1.26: Worker state machine with ACTIVE/DRAINING/PENDING_REMOVAL states.

## Changes
- `sys/netgraph/ng_pppoe_lb.h`: Added `enum worker_state` and `struct worker` definition
- `sys/netgraph/ng_pppoe_lb.c`: Implemented state transitions in worker selection logic

## Verification
- Module compiles successfully (0 errors, 1 warning)
- Existing unit tests pass

## Notes
- Worker hot-remove still needs pppoed integration (Phase 2.5)
- Drain timeout not yet implemented
```

## 7. Merge Conflict Handling

### 7.1 If Another Agent Modified Same File

1. Read the conflicting sections
2. Understand both changes
3. Merge logically (preserve both features if possible)
4. Test merged result
5. Document merge in task notes

### 7.2 If Plan Documents Conflict

1. Check task dependencies
2. Verify which task is authoritative
3. Preserve highest-priority feature
4. Document resolution in task notes

## 8. Multi-Agent Coordination

### 8.1 Parallel Task Types

These task types can run in parallel:
- Phase 1 tasks (kernel module components)
- Phase 2 tasks (userland components)
- Phase 5 tasks (sysctl additions)
- Documentation tasks

### 8.2 Sequential Dependencies

These tasks must run sequentially:
- Phase 1 → Phase 2 (kernel module before userland integration)
- Phase 1.5 → Phase 2.5 (governor design before implementation)
- Module build verification before testing

### 8.3 Communication Protocol

When two tasks might interact:
1. Leave detailed comments in code
2. Update task notes with interaction points
3. Mark blocking dependencies explicitly
