# Auto-Scaling & Governance

## 5.0.1 Overview

The auto-scaling governor monitors system load and dynamically adjusts the number of worker nodes to maintain optimal performance.

---

## 5.0.2 Worker State Machine

```
                    ┌─────────────────────────────────────┐
                    │                                     │
                    v                                     │
┌──────────┐     ┌──────────┐     ┌──────────────────┐   │
│ ACTIVE   │────>│ DRAINING │────>│ PENDING_REMOVAL  │───┘
│          │     │          │     │                  │
└──────────┘     └──────────┘     └──────────────────┘
    ▲                │                    │
    │                │                    │
    │                │                    │
    └────────────────┴────────────────────┘
           (cancel pending removal)
```

**States:**
- `ACTIVE` (0): Normal operation, accepts new sessions
- `DRAINING` (1): No new sessions assigned, existing sessions complete naturally
- `PENDING_REMOVAL` (2): Empty, waiting for actual removal signal

## 5.0.3 Scaling Algorithm

### Scale Up Logic

```
SCALE_UP_TRIGGERED when:
  - (CPU > cpu_threshold AND time_since_last_scale_up > scale_up_interval)
  OR
  - (sessions > sessions_per_worker * workers * 0.8)
  
AND workers < max_workers
AND workers < mp_ncpus

ACTION:
  1. If any worker is PENDING_REMOVAL → CANCEL it (change mind!)
  2. Create new worker
  3. Log: "governor: scale up (reason: cpu_high/sessions_high)"
```

### Scale Down Logic

```
SCALE_DOWN_TRIGGERED when:
  - (CPU < cpu_low_threshold AND time_since_last_scale_down > scale_down_interval)
  OR
  - (sessions < sessions_per_worker * workers * 0.3)
  
AND workers > min_workers

ACTION:
  1. Select worker with fewest active sessions
  2. Mark worker as DRAINING (no new sessions)
  3. After drain_timeout seconds:
     - If sessions == 0 → PENDING_REMOVAL
     - Else → back to ACTIVE (couldn't drain in time)
  4. Signal pppoed to remove worker
  5. Log: "governor: mark worker N for removal"
```

## 5.0.4 "Change Mind" Scenario

```
Timeline:
  T=0:   Governor marks worker 3 for removal (CPU low)
  T=10:  Traffic spike arrives
  T=15:  Governor detects CPU > threshold, wants to scale UP
  T=15:  Governor CANCELS removal of worker 3, marks it ACTIVE
  T=16:  No new worker needed - existing worker 3 serves traffic
  
Result: Avoided creating worker 4, kept worker 3
```

## 5.0.5 Sysctl Configuration

| Sysctl | Default | Description |
|--------|---------|-------------|
| `governor.enabled` | 0 | Enable governor (0=disabled, 1=enabled) |
| `governor.mode` | 0 | Governor mode (0=manual, 1=auto) |
| `governor.min_workers` | 1 | Minimum workers |
| `governor.max_workers` | 0 | Maximum workers (0=auto/mp_ncpus) |
| `governor.poll_interval` | 5 | Poll interval in seconds |
| `governor.cpu_threshold` | 80 | Scale up at CPU % |
| `governor.cpu_low_threshold` | 30 | Scale down at CPU % |
| `governor.sessions_per_worker` | 500 | Target sessions per worker |
| `governor.drain_timeout` | 30 | Drain timeout in seconds |

See [`5.1-PPPoE-Sysctl-Interface.md`](./5.1-PPPoE-Sysctl-Interface.md) for full reference.
