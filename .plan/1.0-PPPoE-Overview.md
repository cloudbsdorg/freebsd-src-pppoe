# Multithreaded PPPoE for FreeBSD — Implementation Plan Overview

## 1.0.1 Executive Summary

This document outlines a comprehensive, incremental approach to adding multithreaded PPPoE support to FreeBSD. The goal is to enable parallel processing of PPPoE sessions to improve throughput and reduce latency on multi-core systems serving many concurrent subscribers.

**Primary Recommendation:** Horizontal scaling via multiple `ng_pppoe` nodes with a session-aware load balancer.

---

## 1.0.2 Problem Statement

FreeBSD's current PPPoE implementation has a critical bottleneck: all PPPoE sessions are processed through a single `ng_pppoe` netgraph node, which becomes the limiting factor on multi-core systems.

**Symptoms:**
- High CPU usage on a single core during heavy PPPoE load
- Session setup latency increases with subscriber count
- Poor utilization of available CPU cores
- Cannot scale beyond single-core performance

---

## 1.0.3 Solution Overview

The solution introduces a **load balancer node** (`ng_pppoe_lb`) that:
1. Accepts discovery packets (PADI) from clients
2. Distributes established sessions across multiple `ng_pppoe` worker nodes
3. Maintains session affinity (same session always goes to same worker)
4. Scales horizontally by adding/removing worker nodes

```
+-------------------------------------------------------------+
|                    Ethernet Interface                        |
|                      (ng_ether node)                         |
+----------------------------+--------------------------------+
                             |
                             v
+-------------------------------------------------------------+
|              ng_pppoe_lb (Load Balancer Node)                |
|  - Distributes packets to worker nodes based on session hash |
|  - Handles discovery phase (PADI) broadcast                  |
|  - Manages session-to-node mapping table                     |
+--+-----------+-----------+-----------+-----------+----------+
   |           |           |           |           |
   v           v           v           v           v
+------+   +------+   +------+   +------+   +------+
|pppoed|   |pppoed|   |pppoed|   |pppoed|   |pppoed|
|  #0  |   |  #1  |   |  #2  |   |  #3  |   |  #N  |
+------+   +------+   +------+   +------+   +------+
```

---

## 1.0.4 Key Design Principles

1. **Minimal changes to existing code:** Reuse `ng_pppoe` as-is, add new components
2. **Leverage existing netgraph parallelism:** Each worker node runs on different threads
3. **Session affinity:** All packets for a given session go to the same worker node
4. **Incremental deployment:** Can start with 1 node (current behavior) and scale up
5. **Auto-scaling support:** Governor monitors load and adjusts worker count automatically

## 1.0.6 Data Structures

### Load Balancer Node Private Data

```c
struct ng_pppoe_lb_private {
    struct nodeinfo       nodeinfo;              // Standard node info
    struct mtx            lock;                  // Global lock
    int                   debug;                 // Debug level

    // Worker management
    struct worker        *workers;               // Array of workers
    int                   num_workers;           // Current worker count
    int                   active_workers;        // ACTIVE workers only

    // Session affinity
    struct sess_map      *session_map;           // Session ID → worker mapping
    int                   sess_count;            // Total active sessions

    // Configuration
    int                   algorithm;              // 0=round-robin, 1=hash, 2=least-loaded
    int                   max_sessions;           // Per-node session limit
    int                   enable_governor;       // Auto-scaling enabled

    // Statistics
    struct stats          stats;                 // Counters and metrics
};
```

### Worker Node

```c
struct worker {
    int                   id;                   // Worker ID
    enum worker_state     state;                 // ACTIVE/DRAINING/PENDING_REMOVAL
    node_p                node;                  // ng_pppoe node
    hook_p                hook;                 // Lower hook to ng_pppoe

    // Session tracking
    int                   sessions;             // Active sessions on this worker
    struct timeval        last_activity;       // Last session activity

    // Metrics
    struct timeval        created;              // Creation timestamp
    atomic_t              packets_in;           // Packets in
    atomic_t              packets_out;          // Packets out
};
```

### Worker States

| State | Value | Description |
|-------|-------|-------------|
| `ACTIVE` | 0 | Normal operation, accepts new sessions |
| `DRAINING` | 1 | No new sessions, waiting for existing to complete |
| `PENDING_REMOVAL` | 2 | Empty, marked for removal |

## 1.0.7 Sysctl Interface

The load balancer exposes a comprehensive sysctl interface for monitoring and control:

```
net.graph.pppoe_lb
├── debug                          # Debug level (0-5)
├── node.hook                      # Node hook name
├── session.max                    # Max sessions per worker
├── session.total                  # Total active sessions (read-only)
├── algorithm                      # 0=round-robin, 1=hash, 2=least-loaded
├── algorithm.name                 # Algorithm name (read-only)
│
├── governor.enabled              # Governor enabled (0/1)
├── governor.mode                 # 0=manual, 1=auto
├── governor.min_workers          # Minimum workers (default: 1)
├── governor.max_workers         # Maximum workers (0=mp_ncpus)
├── governor.poll_interval        # Governor poll interval (seconds)
├── governor.cpu_threshold       # Scale up at CPU %
├── governor.cpu_low_threshold  # Scale down at CPU %
├── governor.sessions_per_worker # Target sessions per worker
├── governor.drain_timeout       # Drain timeout in seconds
│
├── governor.current_workers     # Current worker count (read-only)
├── governor.active_workers      # ACTIVE workers (read-only)
├── governor.draining_workers   # DRAINING workers (read-only)
├── governor.pending_removals   # Workers pending removal (read-only)
├── governor.last_decision       # Last scaling decision
├── governor.last_reason         # Last decision reason
│
├── workers.count                 # Worker count
├── workers.{id}.state          # Worker state (READ/WRITE)
├── workers.{id}.sessions       # Sessions on worker (read-only)
├── workers.{id}.last_activity  # Last activity timestamp
├── workers.{id}.uptime         # Worker uptime in seconds
│
├── stats.packets_in             # Total packets in
├── stats.packets_out            # Total packets out
├── stats.bytes_in               # Total bytes in
├── stats.bytes_out              # Total bytes out
├── stats.session_creates        # Sessions created
├── stats.session_teardowns      # Sessions torn down
└── stats.scale_events           # Scaling events
```

## 1.0.8 Configuration Examples

### Basic 2-Worker Setup

```bash
# Create load balancer node
ngctl mkpeer em0 hook pppoe_lb lb

# Create 2 worker nodes
ngctl mkpeer lb: pppoe lower w1
ngctl mkpeer lb: pppoe lower w2

# Configure workers
ngctl msg lb: setworkers 2
ngctl msg lb: setalgorithm hash
```

### Auto-Scaling Setup

```bash
# Enable governor with auto-scaling
sysctl net.graph.pppoe_lb.governor.enabled=1
sysctl net.graph.pppoe_lb.governor.mode=1
sysctl net.graph.pppoe_lb.governor.min_workers=2
sysctl net.graph.pppoe_lb.governor.max_workers=0   # 0 = mp_ncpus
sysctl net.graph.pppoe_lb.governor.poll_interval=5
```

## 1.0.9 Risks and Mitigations

| Risk | Severity | Mitigation |
|------|----------|------------|
| Single point of failure | Medium | Redundant load balancers |
| Session migration complexity | Medium | DRAINING state prevents new sessions |
| Lock contention at scale | Medium | Per-worker locks, hash table optimization |
| Governor misprediction | Low | Conservative thresholds, long intervals |

See [`7.0-PPPoE-Risks.md`](./7.0-PPPoE-Risks.md) for detailed analysis.

## 1.0.12 Conclusion

The proposed architecture provides:
- **Horizontal scaling**: Add workers to utilize more CPU cores
- **Session affinity**: Consistent session routing to same worker
- **Auto-scaling**: Governor adjusts worker count based on load
- **Minimal impact**: Existing single-worker mode remains supported
- **Incremental deployment**: Start simple, add features as needed

This approach balances complexity with capability, providing immediate benefit while enabling future enhancements.
