# Alternative Approaches Considered

## 6.0.1 Approaches Evaluated

### Approach A: Single Node with Parallelism (REJECTED)

**Description:** Add parallel processing to existing `ng_pppoe` node.

**Rejection Reason:**
- Requires significant changes to existing, stable code
- High risk of regressions
- Limited scalability (still single node bottleneck)

### Approach B: Userland Packet Processing (REJECTED)

**Description:** Move PPPoE processing to userland with kernel bypass (like netmap).

**Rejection Reason:**
- Major architectural change
- Loses kernel integration benefits
- Complex implementation

### Approach C: Multiple Independent ng_pppoe Nodes (REJECTED)

**Description:** Create multiple standalone `ng_pppoe` nodes, use ECMP for distribution.

**Rejection Reason:**
- No session affinity (sessions may be split)
- Requires external load balancer
- Complex setup

### Approach D: Load Balancer Node (ACCEPTED) ✓

**Description:** Add `ng_pppoe_lb` node in front of multiple `ng_pppoe` workers.

**Acceptance Reason:**
- Minimal changes to existing code
- Session affinity maintained
- Incrementally deployable
- Auto-scaling support built-in
